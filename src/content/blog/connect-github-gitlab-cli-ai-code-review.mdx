This is not a new trick. GitHub CLI and GitLab CLI have existed for a while, and coding agents have been able to call terminal tools for a while too. But I still meet developers who use agents only inside the editor and forget that the agent can also read pull requests, inspect merge requests, comment on them, check CI, and help prepare a better review for humans.

My current habit is simple: before I send a merge request to coworkers, I ask a coding agent to review it first. It is not a replacement for team review. It is a pre-review pass. The agent catches boring mistakes, missing tests, suspicious edge cases, unclear naming, and sometimes real bugs. Then my coworkers spend less time on obvious issues and more time on product and architecture.

Ideally, this should be integrated into CI. A manual local workflow is useful, but a repeatable pipeline review is better: same prompt, same scope, same permissions, same audit trail.

## Install the CLIs

For GitHub, install [GitHub CLI](https://cli.github.com/manual/):

```bash
# macOS
brew install gh

# Debian / Ubuntu
sudo apt install gh

# Fedora
sudo dnf install gh

# Arch Linux
sudo pacman -S github-cli

# Windows
winget install --id GitHub.cli
```

Package names and repositories can differ by distro. If your package manager does not have a recent `gh`, use the installation instructions from the official GitHub CLI manual.

Then authenticate:

```bash
gh auth login
gh auth status
```

For headless environments, GitHub CLI can use a token from the environment:

```bash
export GH_TOKEN=github_pat_...
gh pr view 123
```

The official `gh auth login` docs also support `--with-token` for reading a token from stdin, but for automation I usually prefer an environment variable because it is explicit and easy to inject in CI.

For GitLab, install [GitLab CLI](https://docs.gitlab.com/cli/):

```bash
# macOS
brew install glab

# Linux
# Use your distribution package if available, or download a binary from GitLab CLI releases.

# Windows
winget install --id GitLab.glab
```

GitLab documents Homebrew as an officially supported package manager for macOS, Linux, and Windows through WSL. On native Linux and Windows, I would still check the current GitLab CLI install page because package availability changes by distro and environment.

Then authenticate:

```bash
glab auth login
glab auth status
```

For GitLab Self-Managed, pass the hostname:

```bash
glab auth login --hostname gitlab.company.com
```

You can also use environment variables, which is usually the easiest path for agents and CI:

```bash
export GITLAB_HOST=https://gitlab.company.com
export GITLAB_TOKEN=glpat-...

glab mr view 123
```

GitLab documents `GITLAB_HOST` / `GL_HOST`, `GITLAB_TOKEN`, and `GLAB_ENABLE_CI_AUTOLOGIN`. In GitLab CI, `GLAB_ENABLE_CI_AUTOLOGIN=true` can let `glab` use predefined CI variables such as `CI_SERVER_FQDN` and `CI_JOB_TOKEN` for commands that support job-token authentication.

## Give your agent the right tools

Once `gh` or `glab` works in your terminal, most coding agents can use it too. The useful part is not just "AI can see my repo." The useful part is that the agent can query the same review surface your team uses.

For GitHub:

```bash
gh pr view 123 --comments
gh pr diff 123
gh pr checks 123
gh pr review 123 --comment --body "Reviewed locally with an AI agent. See notes above."
```

For GitLab:

```bash
glab mr view 123
glab mr diff 123
glab mr note 123 --message "Reviewed locally with an AI agent. See notes above."
glab ci status
```

Then ask the agent something concrete:

```text
Review MR 123 using glab.
Focus on regressions, missing tests, security issues, and behavior changes.
Do not comment on style unless it can hide a bug.
Return findings ordered by severity with file references.
```

This is much better than "review my code", because it tells the agent where to look and what kind of feedback matters.

## GitLab Behind Basic Auth

At one company, our GitLab was self-managed and hidden behind an extra HTTP Basic Auth layer. The GitLab token was valid, but requests still failed before they reached GitLab because the reverse proxy asked for Basic Auth first.

This is not a way to bypass security. You still need authorized credentials for both layers:

1. HTTP Basic credentials for the company proxy.
2. A GitLab token for the GitLab API.

One practical workaround is to include the Basic Auth credentials in the GitLab URL that the CLI uses:

```bash
export GITLAB_HOST="https://basic_user:basic_password@gitlab.company.com"
export GITLAB_TOKEN="glpat-..."

glab api user
glab mr view 123
```

For `git` operations, you may need the same idea in the remote URL or in your credential helper:

```bash
git remote set-url origin "https://basic_user:basic_password@gitlab.company.com/group/project.git"
```

Be careful with this. URLs with credentials can leak into shell history, logs, process lists, config files, and screenshots. Prefer short-lived credentials where possible. If your environment supports it, store them in a credential manager instead of hardcoding them into remotes. In CI, put them in masked variables and build the URL only inside the job.

A CI-flavored version looks like this:

```bash
export GITLAB_HOST="https://${BASIC_AUTH_USER}:${BASIC_AUTH_PASSWORD}@gitlab.company.com"
export GITLAB_TOKEN="${GITLAB_API_TOKEN}"

glab mr view "$CI_MERGE_REQUEST_IID"
```

If your GitLab proxy uses custom headers instead of Basic Auth, this exact pattern will not apply. In that case, check whether your CLI, proxy, or CI runner can inject the required header. If not, a small internal proxy that adds the header may be cleaner than putting credentials into every tool.

## Let Agents Review MRs

After CLI access works, the workflow becomes straightforward:

```text
Use glab to review the current merge request.
Check the MR description, diff, discussions, and pipeline status.
Find only issues that could cause bugs, production regressions, security problems,
missing tests, or confusing behavior for users.
Do not approve or post comments until I confirm.
```

I usually ask for a local report first. If the findings are useful, I fix them before asking coworkers. If I want the agent to post to the MR, I ask it explicitly and review the text before it sends anything.

Good agent review prompts are narrow:

- "Review only the diff against `main`."
- "Focus on auth and permission regressions."
- "Check whether the tests cover the changed behavior."
- "Compare the implementation with the issue description."
- "Summarize unresolved reviewer comments."
- "Find the smallest safe fix for the failing pipeline."

Bad prompts are vague:

- "Review everything."
- "Make it better."
- "Fix all problems."

The agent is most useful when it has clear boundaries.

## Use Different Agents Against Each Other

Another useful pattern is to split generation and review between different agents or models.

For example:

1. Ask Claude to implement a feature.
2. Ask OpenCode with a DeepSeek model to review the diff.
3. Copy the review findings back to Claude.
4. Ask Claude to fix only the confirmed issues.
5. Review the final diff yourself before asking coworkers.

This gives you some model diversity. If one agent generated the code, another agent may notice assumptions the first one missed. It is still not a guarantee. Two agents can agree on the same wrong idea. But in practice, a second independent pass is often better than asking the same agent to check its own work immediately after writing it.

I like prompts like this for the review agent:

```text
Review this diff as if it was written by another AI agent.
Do not assume the implementation is correct.
Look for hidden regressions, missing tests, incorrect edge cases,
security problems, and behavior that does not match the MR description.
Return only actionable findings.
```

Then I pass the findings back to the implementation agent:

```text
Here is an external review of your change.
Fix only the valid issues.
If you disagree with a finding, explain why before changing code.
Keep the scope minimal.
```

This loop is especially useful when the original code was mostly generated by an agent. I do not want the same tool to be the only author and the only reviewer.

## CI Is the Better Version

Manual review is good for personal workflow. CI review is better for teams.

A CI job can:

- run only on pull requests or merge requests;
- use a locked prompt committed to the repo;
- keep credentials in CI secrets;
- post the result back to the PR or MR;
- avoid depending on a developer's laptop setup;
- make the review auditable.

OpenCode has a documented [GitLab integration](https://opencode.ai/docs/gitlab/) that runs through GitLab CI and can review merge requests with `@opencode review this merge request`. Codex has docs for [GitHub code review](https://learn.chatgpt.com/docs/third-party/github) and the [Codex GitHub Action](https://learn.chatgpt.com/docs/github-action), including automatic PR reviews and CI workflows. Claude Code has docs for [GitHub Actions](https://code.claude.com/docs/en/github-actions) and [GitLab CI/CD](https://code.claude.com/docs/en/gitlab-ci-cd).

Other agents usually have similar instructions. The pattern is almost always the same:

1. Store the model/API credentials as CI secrets.
2. Give the job read access to the repository and MR/PR metadata.
3. Fetch the diff.
4. Run the agent with a strict review prompt.
5. Post a review comment or fail the job only for high-confidence issues.

I would be careful with hard CI gates at first. Start by posting comments. After the prompt is stable and the signal is good, then consider failing the pipeline for specific classes of findings.

## My Current Rule

My rule is not "AI reviews instead of people." My rule is:

1. I review my own code.
2. I ask a coding agent to review it.
3. If the code was generated by one agent, I may ask a different agent or model to review it.
4. I fix the obvious issues.
5. Then I ask coworkers to review it.

That order respects other people's time. It also makes human review better, because teammates are less likely to spend attention on things I could have caught myself with one extra pass.

The setup is small: authenticate `gh` or `glab`, verify the agent can use the CLI, and start with read-only review prompts. The payoff is that every MR gets one more serious look before it reaches the team.
