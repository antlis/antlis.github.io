# Controlling mpv on My Homeserver TV via Telegram and Hermes Agent

My homeserver sits in the living room with an HDMI cable to the TV. For a long time the only way to start something playing was to walk over, switch the keyboard, and type. That's fine for one movie. It's miserable for cartoons-on-shuffle while I'm cooking.

So I wired the whole thing up to Telegram. Now the TV is a media box I control from my phone — the same surface I use for everything else. Two control paths sit on top of one mpv instance:

- **Quick commands** (`/mpv_pause`, `/mpv_play lain`) — instant, no LLM call, zero tokens.
- **Natural language** ("pause that", "play something with robots") — routed through the [Hermes agent](https://hermes-agent.nousresearch.com/) (Nous Research) running `hermes-medium` via [nanogpt](https://nano-gpt.com/) (I'm on the $12/month subscription, which is plenty for a personal remote — see the caveat further down).

This post walks through how it's wired together, the IPC trick that makes it all work, and the subtle gotchas that ate hours of my life.

## The Architecture

```
┌─────────────┐       ┌──────────────────┐       ┌──────────────┐
│  Telegram   │──────▶│  Hermes Gateway  │──────▶│   mpvctl.sh  │
│   (phone)   │       │   (homeserver)   │       │   (script)   │
└─────────────┘       └────────┬─────────┘       └──────┬───────┘
                               │                        │
                       (LLM route only)                 │ JSON-IPC
                               │                        ▼
                       ┌───────▼────────┐       ┌──────────────┐
                       │  hermes-medium │       │     mpv      │
                       │   via nanogpt  │       │ (i3 ws 10)   │
                       └────────────────┘       └──────┬───────┘
                                                       │ HDMI
                                                       ▼
                                                 ┌──────────┐
                                                 │    TV    │
                                                 └──────────┘
```

The key insight: **Telegram messages either short-circuit to a shell script (zero tokens) or go through the LLM (when the request needs reasoning).** Both paths end up speaking to the same mpv instance through a Unix domain socket.

## The mpv Side

mpv runs on the homeserver's X session (`DISPLAY=:0`), pinned to i3 workspace 10. It's launched with an IPC socket so anyone with shell access can drive it:

```bash
mpv --input-ipc-server=/tmp/mpv-socket \
    --force-window \
    --playlist=/path/to/something.m3u
```

`--input-ipc-server` is the magic flag. mpv opens `/tmp/mpv-socket` as a Unix domain socket and accepts JSON commands. Pause becomes:

```bash
python3 -c "
import socket
s = socket.socket(socket.AF_UNIX)
s.connect('/tmp/mpv-socket')
s.send(b'{\"command\":[\"set_property\",\"pause\",true]}\n')
s.close()
"
```

(I'd love to use `socat` here. It's not installed on this box. Python it is.)

`--force-window` matters: without it, mpv refuses to open a window until media starts loading, which makes the "playlist is empty / starting up" race visible. With it, the window is always there.

### The mpv-runner wrapper

When mpv is launched from a non-graphical context (a Telegram bot, systemd, a tmux pane on another tty), it needs `DISPLAY` and the i3 IPC socket exported explicitly. Otherwise: audio plays, no window. I figured this out the hard way.

The wrapper at `/tmp/mpv-runner.sh`:

```bash
#!/bin/bash
export I3SOCK="/run/user/1000/i3/ipc-socket.2012"
export DISPLAY=:0
exec mpv "$@"
```

One catch: `/tmp` is tmpfs on this box, so the wrapper disappears on reboot. The mpvctl script checks it exists before every launch and recreates it if missing. This was the #1 cause of "the bot says it played but nothing happened" bugs.

## The mpvctl.sh Dispatcher

Everything Telegram-facing routes through one shell script: `~/.hermes/scripts/mpvctl.sh`. It takes a subcommand (`pause`, `play`, `volup`, `list`, ...) and either talks to the IPC socket or — for `play` — launches a new mpv instance.

The interesting bit is the launch case. Naïvely:

```bash
nohup /tmp/mpv-runner.sh --playlist="$MATCH" ... &
disown
```

This works fine when you run it from a terminal. It **fails** when the gateway runs it via `asyncio.create_subprocess_shell` with captured pipes — there's no controlling TTY for `nohup` to detach from, and the script gets SIGTERM'd along with mpv the moment it exits. Result: return code -15, no output, mpv never appears.

The fix is `setsid`:

```bash
setsid /tmp/mpv-runner.sh \
    --playlist="$MATCH" \
    --input-ipc-server="$SOCKET" \
    --force-window \
    </dev/null >/dev/null 2>&1 &
```

`setsid` forks a new OS session, fully decoupled from whatever started the script. Combined with `</dev/null >/dev/null 2>&1` to detach the inherited pipe file descriptors, the script returns immediately and mpv keeps running.

## Wiring It to Telegram: Quick Commands

This was a hard requirement when I started building the setup: the everyday verbs — pause, resume, skip, list — must not call the LLM. They get used dozens of times a day, and if every tap on `/mpv_pause` chewed through tokens I'd be staring at the nanogpt usage panel by Wednesday. So I needed an LLM-free route.

Hermes supports exactly this through a top-level config key called `quick_commands` in `~/.hermes/config.yaml`. Anything registered there is matched by the Telegram gateway *before* the agent loop, dispatched as a plain shell exec, and the script's stdout is sent back to Telegram as the response. **No model call. No tokens. Zero contribution to the weekly quota. Instant.**

Quick commands aren't on by default in the sense that they need entries — there's no automatic bridge from "this verb is repetitive" to "this verb gets a shell shortcut." You opt each one in by listing it in the `quick_commands:` block. Here's mine:

```yaml
quick_commands:
  mpv_pause:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh pause
  mpv_unpause:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh unpause
  mpv_quit:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh quit
  mpv_volup:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh volup
  mpv_voldown:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh voldown
  mpv_mute:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh mute
  mpv_list:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh list
  mpv_info:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh info
  mpv_fwd:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh fwd
  mpv_back:
    type: exec
    command: /home/username/.hermes/scripts/mpvctl.sh back
  mpv_play:
    type: exec
    command: /bin/bash /home/username/.hermes/scripts/mpvctl.sh play {{ARGS}}
  mpv:
    type: exec
    command: /bin/bash /home/username/.hermes/scripts/mpvctl.sh play {{ARGS}}
```

Two non-obvious things in here:

1. **Underscores, not hyphens.** Telegram delivers `/mpv_list` as the command name `mpv_list` (with underscore). The lookup in the gateway is exact-match. I burned an evening on this — using `mpv-list` in the config silently routes to "Unknown command."

2. **`/bin/bash` prefix on the launching commands.** Same root cause as the `setsid` issue. The gateway runs these via asyncio subprocess with captured pipes. A direct script path returns SIGTERM (-15) and never launches mpv. Wrapping in `/bin/bash` works around the asyncio non-TTY behaviour. The non-launching commands (`pause`, `volup`, etc.) don't need it because they exit cleanly without spawning children.

The `{{ARGS}}` placeholder gets shell-escaped through `shlex.quote()` and passed in, so `/mpv_play "lain";rm -rf ~` doesn't do what it looks like it could do. That `shlex.quote` happens inside the gateway's exec handler — peeking at the relevant chunk of `gateway/run.py`:

```python
# Sanitize env to prevent credential leakage —
# quick commands run in the gateway process which
# has all API keys in os.environ.
from tools.environments.local import _sanitize_subprocess_env
sanitized_env = _sanitize_subprocess_env(os.environ.copy())
proc = await asyncio.create_subprocess_shell(
    exec_cmd,
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
    env=sanitized_env,
)
stdout, stderr = await asyncio.wait_for(proc.communicate(), timeout=30)
output = (stdout or stderr).decode().strip()
# Redact any remaining sensitive patterns in output
if output:
    from agent.redact import redact_sensitive_text
    output = redact_sensitive_text(output)
return output if output else "Command returned no output."
```

There are three nice defenses-in-depth here that I didn't have to write:

- **Environment sanitization** strips API keys from `os.environ` before the script runs, so my shell scripts can't accidentally `env | tg-message` something terrible.
- **30-second hard timeout** keeps a buggy script from wedging the gateway's command loop.
- **Output redaction** runs over whatever the script prints, scrubbing anything that looks like an API key before Telegram ever sees it.

For a tool that turns "the entire process environment of my Telegram bot" into "shell scripts triggered by anyone in `allowed_chats`," that's a comforting set of guardrails.

## The Quick Commands in Use

After registering these (and remembering to `deleteMyCommands` for any leftover scope-specific overrides — those silently shadow the default scope), my Telegram bot menu has the full remote:

| Command | What it does |
|---|---|
| `/mpv_pause` | Pause |
| `/mpv_unpause` | Resume |
| `/mpv_quit` | Stop |
| `/mpv_volup` / `/mpv_voldown` | ±10 volume |
| `/mpv_mute` | Toggle mute |
| `/mpv_fwd` / `/mpv_back` | Seek ±30s / -10s |
| `/mpv_list` | List all playlists |
| `/mpv_info` | Show what's playing |
| `/mpv_play <name>` | Fuzzy-match and start a playlist |

The `play` command searches three folders in order — `~/Videos/cartoons/playlists/`, `~/Videos/movie/playlists/`, `~/Videos/shows/playlists/` — and grabs the first `.m3u` whose name contains the search term (case-insensitive). So `/mpv_play lain` finds `serial-experiments-lain.m3u`, `/mpv_play deadwood` finds `Deadwood.m3u`, etc. If you pass a number instead, it indexes into the sorted list from `/mpv_list`.

## The LLM Path: nanogpt + hermes-medium

The quick commands handle 95% of what I want. The remaining 5% is requests that need actual interpretation:

- "play something with robots in it"
- "what was that show with the post-apocalypse highway"
- "skip ahead to the part where the music kicks in"

For these I configured Hermes to use **`hermes-medium`** served by **[nanogpt](https://nano-gpt.com/)** as an OpenAI-compatible endpoint. I'm on the **$12/month subscription tier** — for a chatty TV remote, the monthly flat fee is much friendlier than per-token billing. nanogpt also fronts a bunch of other open-weight models, so the same key works if I want to A/B another model from `model-presets.json`.

The provider config in `~/.hermes/config.yaml`:

```yaml
providers:
  nanogpt:
    api_key: sk-nano-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
    base_url: https://nano-gpt.com/api/v1
```

And the model preset entry that selects `hermes-medium` against that endpoint (`~/.hermes/model-presets.json`):

```json
{
  "id": "nano-medium",
  "label": "⚡ Nano GPT / Hermes Medium",
  "provider": "custom",
  "model": "hermes-medium",
  "base_url": "https://nano-gpt.com/api/v1"
}
```

Switching is `/model nano-medium` in any Hermes chat. The gateway writes the choice back to `model-presets.json` under `current` so it persists across restarts.

When the message can't be matched as a quick command, the gateway forwards it to the model with the mpv skill loaded into context. The skill lives at `~/.hermes/skills/productivity/mpv-playlist-controller/SKILL.md` — it's a markdown file with frontmatter that teaches the model the same set of operations the shell script knows about, plus the file-matching logic, plus permission to call `terminal()` with `background=true` to spawn mpv directly when natural language is involved:

```yaml
---
name: mpv-playlist-controller
description: Control mpv media player for playlists. List, play, pause, stop, mute cartoon playlists from Telegram.
trigger: "play playlist, mpv, pause video, stop video, mute video, list cartoons, list playlists, what cartoons do I have, show me cartoons, what playlist"
---
```

The `trigger` line is what makes the skill auto-load when the user says "play lain" or "list cartoons." No `/skill` invocation needed — the gateway sees a matching keyword and slips the SKILL.md into the model's system prompt. References (`references/ipc-commands.md`, `references/user-environment.md`, etc.) are linked from the SKILL.md and pulled in as needed.

Two routes, one mpv. The script handles the verbs I know I'll repeat; the model handles whatever I happen to say.

## Why Hermes-Medium and Not Something Bigger

A few practical reasons:

- **Latency.** This is interactive — I want the bot to start playback in seconds, not after a 10-second cloud round-trip on a frontier model.
- **The job is small.** Picking between `pause`, `seek`, `play <name>`, and `list` does not need a 200B-parameter model. `hermes-medium` is more than capable.
- **Cost.** The $12/month nanogpt plan covers basically unlimited usage *at this scale*. Pay-per-token APIs would cost roughly the same per month if I'm chatty, with the added downside of bill anxiety.

If you have a beefier server, running an mpv controller against a local llama.cpp would be even cheaper and faster. nanogpt is the path of least resistance.

### A Caveat About "Unlimited"

The "$12 is basically unlimited" framing holds *for the TV-remote use case* — quick commands skip the model entirely, so they cost nothing against any quota. But here's a detail worth knowing if you're going to use Hermes for anything beyond that: nanogpt's plan isn't actually monthly. It's a **weekly quota of 60M input tokens that resets every 7 days, with no carry-over**. Around 8.57M tokens per day is the break-even line.

For mpv remote-control traffic that's never a concern. But once you point Hermes at real agentic work — coding sessions, long debugging chats, anything that builds up context — the burn rate spikes. A single heavy afternoon can eat a quarter of the week's allowance. When you cross the cap, nanogpt doesn't bill extra — it deprioritizes you and the model gets noticeably slower until reset.

I wrote a separate post on [decoding the Hermes status bar and the compression settings that actually slow the burn](/blog/hermes-status-bar-token-tweaks). The TL;DR: drop `compression.threshold` from `0.6` to `0.45`, take `/new` seriously, and don't paste big tool outputs back into the conversation. If you're going beyond `/mpv_play lain`, that's worth a read before the weekly reset clock catches up.

## Lessons from Wiring This Up

If I were doing this over from scratch, I'd save myself the following:

1. **Always test the launch path through whatever pipe-capturing harness will actually run it.** A script that works in your terminal is not the same as a script that works under `asyncio.create_subprocess_shell` with `stdout=PIPE`. Use `setsid`, not `nohup`.

2. **`/bin/bash <script>` is not equivalent to `<script>` under asyncio.** Even with the shebang. I don't fully understand why, but the behaviour is reproducible: the bash prefix works, the direct path SIGTERMs.

3. **tmpfs files vanish on reboot.** Don't put anything load-bearing in `/tmp` without a "create if missing" check. The `mpv-runner.sh` wrapper bit me twice before I added the existence check.

4. **Telegram bot command names use underscores.** Always. Don't try to be cute with hyphens.

5. **Telegram command scopes shadow the default.** If you ever registered commands with `{"scope": {"type": "all_private_chats"}}`, those override the default in the bot menu for private chats. `getMyCommands` (default scope) will lie to you about what your phone sees. Call `deleteMyCommands` for each scope you set, or re-register against the right scope.

6. **`--force-window` on mpv.** Without it, an empty playlist or slow load leaves no visible window and you have no idea whether mpv crashed or is "thinking."

7. **Lean on the gateway's redaction and env-sanitization.** I didn't trust them initially and built my own layer on top. Then I read `gateway/run.py` and realized the gateway is already wiping `os.environ` and post-redacting subprocess output. My redundant layer was just extra surface area. Take the win.

## What This Is Actually Like to Use

I sit on the couch. I open Telegram. I tap `/mpv_play lain` from the bot menu. Two seconds later i3 switches to workspace 10 and Serial Experiments Lain starts on the TV. I tap `/mpv_pause` when the doorbell rings. I tap `/mpv_unpause` afterwards.

If I forget what's in the rotation, `/mpv_list` dumps everything. If I'm too lazy to scroll, "play something noir" gets routed through the LLM and it picks for me.

Total marginal effort versus a "real" Android-TV-style remote: similar. Total infrastructure cost: a shell script, twelve lines of YAML, and a $12/month nanogpt subscription. Total satisfaction at having turned a TV into something I can drive from `urllib.request`: substantial.
